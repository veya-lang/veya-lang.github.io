The Veya guide

This guide covers everything in Veya 0.1, from the syntax to the tools and the standard library.

The language in one page

# methods: typed parameters, inferred locals, implicit return
def greet(name : String, loud : Bool = false) : String
  msg = "Hello, #{name}!"
  loud ? msg.upcase : msg
end
puts greet "Ferris", loud: true      # optional parens, keyword args
def square(x : Int) = x * x          # endless methods

# blocks: yield is inlined; next/break/return work like in Ruby
def twice
  yield 1
  yield 2
end
twice { puts it * 10 }               # `it` = the single block parameter
first_big = sizes.each { |s| break s if s > 1_000 }   # first_big : Int?

# struct = value type (copied), class = reference type (shared, refcounted)
struct Point
  getter x : Float, y : Float
  def +(o : Point) = Point.new(x + o.x, y + o.y)
end
class Player
  property name : String
  @score : Int = 0
  def initialize(@name : String)
  end
end

# nil is only allowed where the type says so
def city(user : User?) : String
  user&.address&.city || "unknown"
end
if (email = user.email)              # email : String inside the if
  send_welcome(email)
end
return "nothing" unless n            # n is non-nil after this line

# enums with data, exhaustive pattern matching
enum Event
  Click(x : Int, y : Int)
  Key(code : Symbol)
  Quit
end
case event
in Click(x:, y:) if x > 0 then draw(x, y)
in Click                 then nil
in Key(code: :esc)       then close
in Key(code:)            then type(code)
in Quit                  then exit
end                      # leave out a branch and it doesn't compile

# integers trap on overflow; wrapping is explicit
Int::MAX + 1             # error: integer overflow in +
Int::MAX &+ 1            # wraps

What's in v0.1

  • Types: Int (64-bit, traps on overflow; literals 1_000, 0xff, 0b1010, 0o755; bitwise &, |, ^, ~, <<, >> with the shift count taken mod 64), Float, Bool, String, Symbol (interned at compile time), Range, Array(T), tuples {Int, String}, T?, struct, class, enum.
  • Type inference: local inference inside methods. Parameters carry types, and return types are inferred unless the method is recursive.
  • Generic methods: def first_or(xs : Array(T), fallback : T) : T. A single capital letter that isn't a type is a type parameter. Each call works the parameters out from its arguments and gets its own copy (first_or<Int>).
  • Generics: class Stack(T), struct Pair(A, B), used as Stack(Int).new or in types (Node(T)?). Each use makes a copy of the type with the parameters replaced (monomorphization, like Rust and C++), so generic code runs as fast as written-out code.
  • Inheritance:
  • class Dog < Animal: a subclass gets its parent's fields and methods and can override them. A Dog goes wherever an Animal is expected, and [Dog.new, Cat.new] is an Array(Animal).
  • A call to a method some subclass overrides is chosen by the object's own class: a hidden type id (the first field) and a switch, since the whole program is known. Calls nobody overrides stay direct.
  • super(args) (super alone passes the same arguments), is_a?, kind_of?, instance_of?, and x.as(Dog) (raises TypeError if it isn't one).
  • p, to_s and to_json show the object's own class.
  • Exception classes: class NotFound < AppError; end (down to StandardError) are raised by name, and rescue AppError catches the kinds below it, including the runtime's own (rescue IndexError catches a KeyError). NotFound.new("msg") is an exception value.
  • Modules:
  • module M ... end with methods to mix in: include M copies them into a class or struct (methods it defines itself win), extend M adds them as class methods. Modules can include modules.
  • self in a module's signatures is the including type: def <(other : self) : Bool.
  • def self.f in a module is a module function, called as M.f(...).
  • abstract def draw : String in a module makes every type that includes it define draw (a compile error names what's missing). In a class, subclasses define it, calls on the base class run the object's own method, and the base class can't be created. See examples/abstract.veya.
  • include Comparable plus <=> gives <, <=, >, >=, ==, between? and clamp (written in Veya: src/prelude/comparable.veya).
  • require_relative "lib/x" (or require "./lib/x") loads another file once.
  • Exceptions:
  • raise "msg", raise ArgumentError, "msg", raise IOError.new("msg"), raise e, and a bare raise in a rescue clause.
  • begin ... rescue Kind1, Kind2 => e ... else ... ensure ... end, also as the body of a def or a do block, retry, and x = expr rescue fallback. Crystal's rescue e : Kind1 | Kind2 and rescue e work too.
  • Kinds are matched by name; rescue => e (or rescue StandardError) catches any. e.message, e.class, e.inspect.
  • The runtime raises IndexError, KeyError, ZeroDivisionError and NilAssertionError. An exception nobody rescues stops the program with its message.
  • ensure runs on return too. break/next out of a begin with ensure isn't supported yet.
  • Exceptions travel as a flag the generated code checks after calls to methods that can raise, and every function leaves through its normal exit, so nothing leaks.
  • Closures:
  • ->(x : Int) { x * 2 }, called with .call. Parameter types can be left out where the Proc type is known.
  • Proc types are written Int -> Int, (Int, String) -> Bool, -> Nil.
  • A method keeps its block with def on(&handler : String -> Nil).
  • &proc passes a Proc where a block goes: [1, 2].map(&square).
  • Captured variables are shared with the method, as in Ruby: they live in a heap cell, so a counter lambda works. Each loop iteration gets its own block variables.
  • next v leaves a lambda with v.
  • Blocks:
  • yield blocks are inlined.
  • &.method and &:sym work as shorthand blocks.
  • it names the single block parameter.
  • loop do ... end loops until break.
  • Iteration:
  • Lazy, fused adapters: map, select, filter, reject.
  • Terminals: each, each_with_index, sum, count, find, any?, all?, none?, reduce, min/max, min_by/max_by, sort_by, flat_map, take_while, each_slice, index, to_a, join.
  • Counting loops: times, upto, downto, step.
  • Control flow: if/elsif/else, unless, while, until, statement modifiers, ternary, case/when with values and ranges, case/in patterns with exhaustiveness checks, multiple assignment.
  • Optionals: &., ||, ||=, .nil?, .not_nil!. Narrowing works on if x, if (x = ...), && and early return. Uninitialized variables are caught at compile time.
  • Strings: "..." interpolates #{}, '...' doesn't. %(say "hi" #{name}) and %Q[...] interpolate too, %q(...) doesn't. Their brackets nest, so quotes need no escaping (handy for JSON). s << "more" (also chained, on a variable or @field) grows a string in place when nothing else holds it, so building one piece by piece is linear; another variable holding the same string keeps the old text. Interpolation, plus upcase, split, gsub, strip, rjust, chars, lines, include?, slicing (including endless ranges, s[3..]), rjust(5, "0") and more.
  • Strings are UTF-8, and sizes and indexes count characters as in Ruby: "zażółć".size is 6, s[0, 2] and reverse keep letters whole, and upcase gives "ZAŻÓŁĆ". bytesize, bytes and byteslice work on bytes.
  • A string remembers whether it's all ASCII, so indexing ASCII text stays O(1).
  • Regular expressions: /(\d+)-(\d+)/i literals, checked while compiling and compiled once at run time.
  • s =~ re gives the position (or nil), plus match?, match ([whole, group1, ...] or nil), scan (groups become arrays), sub/gsub (with \1 in the replacement or a block), split, !~, and case s when /re/.
  • Regex.new(str) raises RegexpError for a bad pattern.
  • Ruby's syntax is translated for the regex crate: ^/$ match at line ends, /m lets . match newlines, \h is a hex digit. There are no backreferences or lookaround.
  • Arrays: %w[a b c], Array.new(n, value), push/<<, pop, shift, first/last (returning T?), [i] (traps when out of range), [i]? (returns nil), slicing, sort, uniq, compact, flatten, +, -, and more. zip (stops at the shorter array), partition { }, to_h (from {key, value} tuples) and each_with_index without a block give or take tuples.
  • Tuples: {1, "a"} has type {Int, String} (also written Tuple(Int, String)).
  • A tuple is stored inline like a struct, compared and hashed by value (so it can be a Hash key), and printed as {1, "a"}. to_json makes it a JSON array.
  • t[0] and t[-1] take an index written in the code, since each element has its own type. first, last, size, and to_a when all elements share a type.
  • a, b = t takes one apart, and so does a block with more parameters than it's given: pairs.each { |name, score| ... }.
  • Methods return several values as a tuple: def min_max(xs : Array(Int)) : {Int, Int}.
  • See examples/tuples.veya.
  • Set: Set(String).new, Set(Int).new([1, 2]), <</add, add?, include?, delete, size, each, to_a, |, &, -, subset?, superset?, ==. It's in insertion order and written in Veya (src/prelude/set.veya).
  • Sorting: sort, sort_by { |x| key }, and sort { |a, b| a <=> b } with a block that compares, all stable.
  • Hash: Hash(K, V), insertion-ordered like Ruby's.
  • Creating: {"a" => 1}, {name: "x"} (Symbol keys), {} of String => Int, Hash(String, Int).new(0) (a default for missing keys).
  • Access: h[k] (an error for a missing key), h[k]? (nil), fetch(k, default), h[k] = v, h[k] += 1, h[k] ||= v.
  • Methods: key?, value?, delete, keys, values, size, empty?, merge, update, clear, dup, ==.
  • With a block |key, value|: each, each_key, each_value, map, select, reject, count, sum, any?, all?, transform_values.
  • Entries as {key, value} tuples: to_a, sort_by, min_by, max_by, find, partition, group_by, reduce, each_with_index, and each { |entry| ... } with one parameter.
  • From arrays: tally and group_by.
  • Keys can be Int, Float, String, Symbol, Bool, structs (compared by value, field by field) and classes (by identity).
  • JSON:
  • Writing: x.to_json and JSON.generate(x) work for every type. Structs and classes become objects. Data enum variants become {"type": "Name", ...}. nil becomes null. A type can define its own to_json.
  • Typed reading: User.from_json(text), Array(User).from_json(text), Hash(String, Int).from_json(text). The reader for each type is generated at compile time and reads what to_json writes, including @[JSON(key: ...)] names. A missing key takes the field's default, or nil for an optional field. Anything else raises JSON::ParseError naming the place: expected an integer for User.id, got a string, or missing key "name" for User.
  • Untyped reading: JSON.parse(text) gives a JSON::Any. Index it with j["key"] / j[0] (a null value when missing) or j["key"]? (nil). Read it with as_s, as_i, as_f, as_bool, as_a, as_s?. It also has size, keys, nil? and to_json. A field can have type JSON::Any to keep part of a document as it is.
  • See examples/json_parse.veya.
  • IO (files, pipes, standard streams):
  • File.open(path, mode = "r") gives an IO; with a block, the file is closed after the block. Modes are "r", "w", "a", each with an optional "+".
  • Reading: gets (a line with its "\n", or nil at the end), each_line { |line| ... } (each_line(chomp: true) drops the newlines), read (the rest), read(n) (up to n bytes, nil at the end), readlines (without newlines), eof?.
  • Writing: puts, print and << take any value (f << "n = " << n << "\n"), write(s) gives the byte count, flush.
  • File.each_line(path) { |line| ... } reads a file of any size line by line.
  • An IO is reference counted: close closes it, and so does dropping the last reference, so files opened in a loop don't run out of descriptors. closed?, fileno, tty?, path.
  • STDIN, STDOUT and STDERR are IO values. STDOUT and STDIN share the buffers of puts and gets, so mixing them keeps the order.
  • Errors raise Errno::ENOENT, Errno::EACCES, IOError (for a closed file, or reading one opened for writing), and so on.
  • See examples/io.veya.
  • Processes:
  • `ls #{dir}` runs a command through the shell and gives what it printed. system("make test") gives true when it exits with 0. Process.last_status is the exit status of the last one.
  • Process.run("git", ["status"]) runs a program without a shell, with the same standard streams, and gives its exit status. Process.capture(cmd, args) gives what it printed.
  • IO.popen("sort") { |io| ... } reads what a command prints ("r", the default) or writes to it ("w"). close gives the exit status.
  • abort("message") prints to stderr and exits with 1. exit(code) flushes output first.
  • Command-line options: OptionParser, written in Veya (src/prelude/option_parser.veya): ruby verbose = false name = "world" files = OptionParser.parse(ARGV) do |o| o.banner = "usage: greet [options] FILE..." o.on("-v", "--verbose", "Say more") { verbose = true } o.on("-n NAME", "--name=NAME", "Who to greet") { |v| name = v } o.on("-h", "--help", "Show this help") { puts o; exit } end
  • parse gives back the arguments that aren't options. A switch with a value name takes a value: -nBob, -n Bob, --name=Bob and --name Bob all work. Short flags combine (-vq), and -- ends the options.
  • o.separator "text" adds a line to the help, and o.help (or puts o) prints it with the switches lined up.
  • An unknown option or a missing value raises OptionError with a message like invalid option: --colour. Uncaught, it prints error: ... and exits with 1.
  • See examples/options.veya.
  • Files and the system:
  • File.read, write, append, readlines, exist?, file?, directory?, size, delete, rename, basename, dirname, extname, expand_path, join.
  • Dir.children, Dir.glob("src/**/*.veya"), Dir.exist?, Dir.mkdir, FileUtils.mkdir_p, Dir.pwd.
  • Failures raise Errno::ENOENT, Errno::EACCES, IOError, and so on.
  • ENV["X"] (a String?), ENV["X"] = v, ENV.fetch, ENV.key?, ENV.keys, STDIN.read.
  • Time.now, Time.local(y, m, d, h, min), Time.at(secs), then year/month/day/hour/min/sec/wday/yday, + seconds, t2 - t1 (a Float), comparisons, strftime, to_s. Time is written in Veya (src/prelude/time.veya).
  • Fibers (concurrency):
  • spawn { ... } runs a block concurrently. Fibers share one OS thread and switch only where they wait: Channel(T)#send/receive, sleep, Fiber.yield. Reference counts stay plain integers and nothing races.
  • Channel(Int).new (unbuffered: send waits for a receiver) or Channel(Int).new(10) (buffered), receive (raises ClosedError when closed), receive? (nil when closed), close, closed?.
  • WaitGroup (add, done, wait) is written in Veya.
  • The program waits for its fibers before it ends. If every fiber waits and none can continue, it stops with "deadlock". An exception nobody rescues in a fiber stops the program.
  • Each fiber has its own stack (256 KB with a guard page). Switching saves the callee-saved registers, a few lines of assembly for arm64 and x86-64.
  • Sockets don't block the other fibers: a fiber waiting on accept, gets, read or write lets the rest run, and the scheduler polls the descriptors when nothing else is ready. Files, pipes and gets on standard input still block every fiber.
  • OS threads (parallelism):
  • t = Thread.new { work(n) } runs a block on its own OS thread. t.value waits and gives its result, t.join waits, t.alive? checks. Four threads on four cores ran a CPU-bound loop 5x faster than one.
  • Threads share nothing. The block works on deep copies of the values it uses, made before it starts. Its result moves to the parent when it's done. So reference counts stay plain integers and there are no data races.
  • Changing a variable from outside in a thread's block is a compile error ("return the result instead"). So is using something that can't be copied, like a Proc, a Channel or a socket.
  • An exception the thread doesn't rescue is raised again by join/value in the parent.
  • Each thread has its own fibers, exception state and random numbers; output from threads goes through one locked buffer.
  • Web apps: Web::App, a small Sinatra-like framework written in Veya (src/prelude/web.veya): ruby app = Web::App.new app.get "/hello/:name" do |c| name = c.params["name"] c.html ECR.render("views/hello.ecr") end app.post "/notes" do |c| notes << (c.form["text"]? || "") c.redirect "/notes" end app.static File.join(__DIR__, "public"), "/static" app.run(3000)
  • Routes for get, post, put, patch and delete, with :name parts and a trailing *. A form's _method=DELETE field stands in for methods HTML forms lack. Unknown paths give 404, a known path with another method 405, and a block that raises gives 500 (logged on stderr).
  • The context c has params, query, form, param(name) (any of them), request (method, path, headers, body), status=, header(name, value), and html, text, json, redirect, not_found to answer.
  • static(dir, prefix) serves files with their MIME types and refuses paths with ... Each request is logged as GET /hello/x 200 4µs unless app.log = false.
  • Underneath is HTTP::Server.new { |req| HTTP::Response.text("hi") } with listen_and_serve(port). It reads HTTP/1.1 with keep-alive, and each connection runs in its own fiber, so a slow client doesn't hold up the others. workers = n forks n processes for n cores.
  • One worker answers about 85k keep-alive requests a second on an M-series Mac (ab -k -c 100), and four reach the limit of ab itself (about 90k).
  • __DIR__ and __FILE__ are the source file's folder and path, as compiled.
  • See examples/web.veya, which starts its server in a child process and checks it with the HTTP client.
  • Templates: ECR.render("views/page.ecr") (the path is relative to the file) is compiled into the program at the place of the call, so the template sees the local variables there, like Crystal's ECR and Ruby's ERB.
  • <%= expr %> puts in expr.to_s, HTML-escaped. <%== expr %> puts it in as it is (a layout's content, say).
  • <% code %> runs code: <% items.each do |i| %> ... <% end %>. <%# comment %>, <%% for a literal <%, and -%> drops the newline after a tag.
  • Errors point at the line of the .ecr file. See examples/templates.veya.
  • Web text: HTML.escape(s), URI.encode_www_form_component(s) / decode_www_form_component(s) (+ for spaces), URI.encode_path_segment / URI.decode (%20).
  • HTTP client: HTTP.get(url), HTTP.post(url, body, headers: {...}), and put, patch, delete, head give an HTTP::Response with status, success?, body and headers (names in lower case).
  • HTTPS uses rustls with Mozilla's root certificates built in, so nothing is needed from the system. Redirects are followed (up to 5) and chunked bodies are decoded.
  • Failures (no connection, a bad certificate, a bad URL) raise HTTP::Error, which is an IOError.
  • TLS is linked only into programs that make requests: hello world stays at 460 KB, and a program using HTTPS is about 1.8 MB.
  • Each request opens its own connection. There's no keep-alive or streaming of big bodies yet.
  • See examples/http.veya.
  • Networking and processes:
  • TCPServer.new(port), then accept, port and close on the server;
  • TCPSocket#gets, read(n), write, << and close, with sockets closed when the last reference is dropped;
  • fork, Process.wait (any child, or Process.wait(pid) for its exit status), Process.kill(pid, signal = 15), Process.pid and Etc.nprocessors.
  • SQLite (built into the runtime): db = Sqlite.open("app.db") (or ":memory:"), db.exec(sql), and db.exec(sql, values) / db.query(sql, values) with ? placeholders filled from an Array(String), so values never become SQL. changes, last_id, close. A query gives a cursor: while st.next, then st.int(i), float(i), text(i), null?(i), name(i), columns. An SQL error stops the program with SQLite's message. See apps/sqlite_demo.veya.
  • Calling C:
  • A lib block declares C functions with C types, and LibZ.crc32(...) calls them. Both backends call C directly, with no wrapper code. ruby @[Link("z")] # -lz; a path to a library works too lib LibZ fun crc32(crc : UInt64, buf : String, len : UInt32) : UInt64 end lib LibC fun getenv(name : String) : String? # NULL is nil fun snprintf(buf : Pointer, n : SizeT, fmt : String, ...) : Int32 fun c_abs = abs(x : Int32) : Int32 # another name end puts LibZ.crc32(0, "hello world", 11)
  • C types: Int8…Int64, UInt8…UInt64, SizeT, Float32, Float64, Bool, Pointer, String (passed as const char *; a result is copied into a new String) and String? (NULL is nil).
  • Arguments are converted at the call. A Veya Int is narrowed to the declared width, and results are widened back.
  • Variadic functions must say ..., since Apple's arm64 passes those arguments differently. Extra arguments go as C's promotions do: Int as int64_t (use %ld), Float as double, String as char *.
  • Pointer is raw memory:
    • Pointer.malloc(n) (zeroed) and free;
    • read_i32(offset = 0), read_u8, read_f64, read_ptr, read_bool and the other widths, each with a matching write_*(offset, value);
    • read_string (up to the NUL), read_string(len) and write_string(offset, s);
    • offset(n), null?, address, Pointer.null and Pointer.new(address).
  • Like in C, nothing checks a pointer's memory: a bad one crashes the program. veya run loads the libraries into the JIT. veya build links them, finding Homebrew's on macOS.
  • See examples/ffi.veya.
  • Globals: puts, print, p, gets, rand, sleep, clock, typeof, assert, exit, ARGV, STDOUT.tty?, Math.*, constants.
  • Macros: macro def, define_method, quote, reflection over fields (see Macros).
  • Error messages: compile errors show your code, a plain-language label and a fix you can paste, with "did you mean" suggestions.

Left out on purpose

eval and ObjectSpace need a runtime that can see and change the program while it runs. Veya compiles ahead of time instead; macros cover most uses of eval.

Quick start

cargo build --release
./target/release/veya run examples/hello.veya      # compiled in memory and run (JIT), ~20 ms
./target/release/veya build app.veya -o app      # optimized native binary
./target/release/veya build --debug app.veya     # for lldb/gdb: breakpoints on .veya lines
./target/release/veya check app.veya             # type-check only
./target/release/veya expand app.veya            # print the program with macros expanded
./target/release/veya fmt app.veya               # re-indent (fmt --check only reports)
./target/release/veya repl                      # interactive session, like irb
cargo test                                       # examples via JIT, executable and C + error messages

Compilation is incremental, in two layers (both in ~/.cache/veya; VEYA_NO_CACHE=1 turns them off):

  • A program whose files, options and compiler are unchanged isn't compiled again; the earlier build is reused.
  • Otherwise each function's machine code is reused when the function is unchanged. Cranelift's incremental cache hashes the function's IR, and calls and data are referenced by name, so editing one method recompiles just that method. With VEYA_TIME=1, after changing one function of apps/json_api.veya: functions: 1 compiled, 34 reused from the cache. This applies to run (JIT) and build.

Checking always covers the whole program, but it takes about a millisecond.

Debug builds (--debug) carry DWARF for the Veya source. Cranelift writes the line table, a compile unit with every function, and .debug_frame from its unwind information, so breakpoints and backtraces work on .veya lines (on macOS dsymutil collects it into app.dSYM):

(lldb) breakpoint set --file primes.veya --line 4
Breakpoint 1: where = primes`f_sieve + 132 at primes.veya:4:3
(lldb) bt
  * frame #0: primes`f_sieve at primes.veya:4:3
    frame #1: primes`main at primes.veya:20:1

With --backend=c --debug the C backend uses #line directives and the C compiler's -g, which also lets the debugger show local variables.

The compiler is one binary with the runtime library embedded in it. It needs only a system linker driver (cc) to link the final executable; set VEYA_LINKER to use a different one.

Backends

backend how when
Cranelift, in memory (default for run) AST → Cranelift IR → machine code in memory, runtime linked into the compiler instant runs: no linker, no files
Cranelift (default for build) AST → Cranelift IR → .o → link with the Rust runtime fast builds, no C compiler needed (run --aot uses this too)
C (--backend=c) AST → C → cc -O2 maximum speed: LLVM optimizes harder (vectorization, inlining)

veya emit-c app.veya prints the C the second backend would compile.

Testing

veya test runs every test/**/*_test.veya (or spec/**/*_spec.veya). It also takes the files or folders to run, and -n name to run only the tests whose name contains it.

require_relative "../src/stack"

describe "Stack" do
  test "pop gives the last push" do
    s = Stack(Int).new
    s.push(1)
    assert_equal 1, s.pop
  end
end

Stack
  ✓ pop gives the last push
  ✗ size counts pushes
      s.size: expected 2, got 1

2 tests, 1 failure (0.01s)
  • What a run does: each file runs as its own program, so one that doesn't compile or crashes is reported and the others still run. A failed assertion ends its test. An exception the test doesn't rescue fails it too.
  • Assertions: assert, refute, assert_equal, assert_not_equal, assert_nil, assert_includes, assert_in_delta, assert_raises("KeyError") { ... } and flunk. They are macros, so a failure names the code that failed.
  • Written in Veya: the framework is in src/prelude/test.veya, and a file that uses it also runs on its own with veya run.
  • See examples/testing.veya.

Projects and packages

veya new shop makes a project:

shop/
  veya.toml          name, main program, dependencies
  src/shop.veya         the library: require "shop"
  src/main.veya         the program: veya run, veya build
  test/shop_test.veya   veya test

Dependencies come from git (a tag, branch or commit) or a local folder:

[package]
name = "shop"
main = "src/main.veya"

[dependencies]
zlib = { git = "https://github.com/someone/zlib.veya", tag = "v1.0" }
util = { path = "../util" }
  • Installing: veya deps installs them, and their own dependencies, into .veya/deps/ (git checkouts, links for folders). It writes veya.lock with the exact commits, so the next veya deps gets the same code anywhere. veya deps update moves to the newest commits the manifest allows.
  • Requiring: require "zlib" loads a package's src/zlib.veya, and require "zlib/inflate" its src/inflate.veya. A project's own tests require it by name the same way.
  • One version per package: if two packages ask for one dependency differently, veya deps says who asked for what.
  • Running and building: in a project, veya run [args] and veya build without a file use the main program. The build is named after the package.
  • Packages can call C: a package can wrap a C library with a lib block (see Calling C). The @[Link] libraries are linked into the program that uses it.

Macros

A macro is a method that runs while compiling (macro def), written in ordinary Veya. There is no separate template language.

macro def counters(*names)
  names.each do |n|
    define_method("add_#{n}") do |by : Int|
      instance_variable_set(n, instance_variable_get(n) + by)
    end
    define_method(n) { instance_variable_get(n) }
  end
end

macro def describable
  define_method(:describe) do
    parts = self.class.fields.map { |f| "#{f.name}=#{f.get(self)}" }
    "#{self.class.name}(#{parts.join(", ")})"
  end
end

class Stats
  @hits : Int = 0
  @misses : Int = 0
  counters :hits, :misses      # runs while compiling
  describable
end

Three rules cover it:

  1. macro def runs while compiling. You call it in a type body (where self is the type) or anywhere an expression can go.
  2. A block given to define_method or quote is code for the running program. Macro values it uses are pasted in, like a closure capturing them:
  3. symbols, strings and numbers become constants;
  4. code (a macro argument, a quote) becomes code.
  5. A loop over compile-time values inside that code is unrolled. This covers self.class.fields.map { ... } and names.each { ... }.

veya expand shows what the compiler sees after macros run:

class Stats
  def add_hits(by : Int)
    @hits = @hits + by
  end
  def hits
    @hits
  end
  ...
  def describe
    parts = ["hits=#{@hits}", "misses=#{@misses}"]
    "Stats(#{parts.join(", ")})"
  end
end

Macros in expressions return code with quote. Quotes are hygienic: a variable the quote assigns gets a fresh name, so quote { tmp = e; tmp + tmp } can't overwrite the caller's tmp. Code passed in as an argument keeps meaning what it meant at the call site, and assigning to such an argument assigns to the caller's variable (a swap!(a, b) macro works). A macro argument is code, and .source gives its text:

macro def show(e) = quote { puts "#{e.source} = #{e}" }
show a * 7                      # prints: a * 7 = 42

macro def fib(n) = n < 2 ? n : fib(n - 1) + fib(n - 2)
puts fib(20)                    # the program only contains 6765

What macros can use:

  • Values: numbers, strings, symbols, arrays, ranges, with the usual methods (each, map, select, join, upcase, ...).
  • Code: e.source, e.literal?.
  • Types: self, fields, methods, has_method?, class?/struct?.
  • Fields: f.name, f.type, f.getter?, and f.get(obj)/f.set(obj, v) in generated code.
  • Inside generated code: instance_variable_get/instance_variable_set and send with a name known while compiling.
  • Errors: raise "..." stops compilation with your message at the macro call.

Hooks run as the program is put together:

  • macro def self.included(base) in a module runs when a type includes it (extended for extend).
  • macro def self.inherited(sub) in a class runs for each subclass. Class macros are inherited.
  • macro def method_missing(name, args) in a class runs while compiling for each call to a method nothing defines. args holds the argument types. It defines the method with define_method and compiling starts over: dynamic finders and attribute proxies without any runtime cost.

Annotations above fields, @[Validate(min_length: 3)], are read by macros (f.annotated?(:Validate), f.annotation(:Validate, :min_length)). to_json honours @[JSON(key: "user_name")] and @[JSON(ignore: true)]. See examples/hooks.veya.

Limits:

  • Macros can't do I/O.
  • They have a step budget, so compiling is deterministic and always finishes.
  • Methods written by hand win over generated ones with the same name.
  • Parameters of define_method blocks need types (|by : Int|), like every method.

Expansion is a separate pass between the parser and the checker (src/macros.rs), so both backends and the REPL see plain code. See examples/macros.veya.

Performance

The timings below come from bench/ on an Apple-silicon Mac. Each column covers the same program written idiomatically in each language.

test Veya (Cranelift) Veya (C backend) Rust (-O) Ruby 4.0 Ruby + YJIT
fib(32) (recursion) 6 ms 5 ms 4–7 ms 102 ms 17 ms
select.map.sum × 50 over 200k structs 14 ms 3 ms 2–6 ms 420 ms 312 ms
float loop, 50M iterations 30 ms 28 ms 27–41 ms 1998 ms 1086 ms

Cranelift generates good code quickly, but it does not vectorize or inline the way LLVM does. Tight loops over structs are about 4× slower than with the C backend. Calls, recursion and float math come out about the same. Build times go the other way:

program Cranelift build C backend build (-O2)
examples/hello.veya 49 ms 76 ms
apps/json_api.veya 54 ms 338 ms

Most of a Cranelift build is the system linker (about 35 ms). Checking takes under 1 ms and code generation under 10 ms. veya run skips linking by compiling into memory:

veya run … in memory (JIT) --aot (link + exec) --backend=c
examples/hello.veya 20 ms 206 ms 353 ms
apps/bank.veya 22 ms 208 ms 247 ms

To reproduce: cd bench && ../target/release/veya build bench.veya -o bench_veya && ./bench_veya (add --backend=c for the second column).

JSON and HTTP

to_json is generated per type at compile time, the way a serde derive works. The benchmark serializes 1000 nested users (230 KB) 1000 times (bench/json/):

serializer time throughput
Veya users.to_json (Cranelift) 104 ms 2.2 GB/s
Veya users.to_json (C backend) 85 ms 2.7 GB/s
Rust serde_json::to_string (derive) 157 ms 1.5 GB/s
Ruby 4.0 JSON.generate(users.map(&:to_h)) 637 ms 0.36 GB/s
Ruby, generator only (hashes pre-built) 281 ms 0.82 GB/s

Reading the same document back, 200 times (best of 5; Cranelift and C backends within a few percent):

parser time throughput
Veya JSON.parse (to JSON::Any) 46 ms 1.0 GB/s
Veya Array(User).from_json (typed objects) 139 ms 330 MB/s
Ruby 4.0 JSON.parse (json 3.1, to hashes) 134 ms 344 MB/s
Ruby, JSON.parse + Struct.new per user 260 ms 177 MB/s

JSON.parse builds the whole document in one arena: - Strings without escapes are slices of the input text. - Each array and object is copied in once, when its bracket closes. - Freeing the document frees a few blocks.

JSON::Any values are small handles, made when a node is read. from_json also allocates the objects and strings it returns.

Veya's serialized output is byte-for-byte identical to Ruby's. The data favors Veya: its scores (i * 1.25) are short decimals, which both backends print with an integer-only fast path. With scores like i / 3.0 the Cranelift backend (whose runtime uses Rust's shortest-float formatting) does 1.45 GB/s, about the same as serde. The C backend's runtime falls back to an snprintf loop there and drops to 200 MB/s.

apps/json_api.veya is an HTTP server written in Veya. It runs against the same API in Rust (std + serde, one thread per worker) and in Ruby (TCPServer + fork). The setup is 4 workers and 4 keep-alive connections, with the load generator on the same machine (bench/http/run.sh). Each number is the median of 3 runs, in req/s:

endpoint Veya (Cranelift) Veya (C) Rust Ruby Ruby + YJIT
GET / (text, 66 B) ~128k ~128k ~132k ~119k ~115k
GET /users/7 (220 B) ~126k ~125k ~128k ~109k ~113k
GET /users (11 KB) ~102k ~103k ~87k ~36k ~51k

Small responses are limited by syscalls and loopback latency, so all the servers score about the same. Once a response carries real serialization work, Veya matches or beats Rust and runs about twice as fast as Ruby. These numbers are noisy, since the machine was running other jobs at the time.

How it works

source ─▶ lexer ─▶ parser ─▶ macros ─▶ checker ──▶ Cranelift IR ─▶ .o ─▶ link with rt (Rust) ─▶ native binary
          (Ruby-style       (run at    (type        └▶ C ─▶ cc (--backend=c)
           tokenizing)       compile    inference,
                             time)      diagnostics)
  • src/lexer.rs: tokens carry a "space before" flag, so foo -1 (a call) and foo - 1 (subtraction) can be told apart the way Ruby does.
  • src/parser.rs: a precedence-climbing parser. It tracks which names are local variables, which is how optional parentheses and command calls work.
  • src/macros.rs: macro expansion, a pass before checking. It holds a small interpreter for compile-time code and the substitution that pastes macro values into generated code. src/printer.rs prints the result for veya expand.
  • src/check.rs: the front end shared by both backends. It type-checks the whole program, produces every diagnostic, and records each function's inferred signature. It assembles a C program only when --backend=c asks for one.
  • src/codegen/: the checker's implementation and the C backend.
  • src/clif/: the Cranelift backend. It reuses the checker's types and signatures and lowers the AST straight to IR.
  • layout.rs: memory layouts. Scalars are SSA values, String/Array/classes are one pointer, and structs, enums, Range and T? of value types live in memory with C-compatible layouts.
  • values.rs: reference counting (inline retain), coercions, strings, and per-type hook functions (drop, retain, ==, to_s, inspect, to_json) generated on demand.
  • calls.rs: calls, constructors, and inlining. Methods that yield are always inlined, and small one-expression methods are inlined too, because Cranelift doesn't inline calls itself. next/break/return become jumps to join blocks.
  • iter.rs: iteration fusion. Adapters wrap the loop body and a terminal drives one loop.
  • patterns.rs: case/when and case/in. Pattern tests branch away early, so other enum variants' fields are never read.
  • link.rs: writes the object file and links it with the embedded runtime.
  • run_jit and repl_eval (in mod.rs): the same code generator over cranelift-jit. Runtime symbols resolve to the copy of rt linked into the compiler, and the program's main runs in the compiler process.
  • src/fmt.rs: the formatter (re-indents from tokens, so comments and spacing inside lines stay). src/lsp.rs: the language server, built on the same front end (check::prepare).
  • src/repl.rs: the REPL loop. Each input becomes a small program made of the accumulated definitions plus the new statements. The checker sees earlier variables as already-assigned locals, and the generated main loads them from session memory and hands them back when it finishes.
  • src/closures.rs: which locals closures capture (a scan by name). Those locals live in heap cells; a closure is {rc, fn, dtor, captures...} and its body is compiled as its own function.
  • src/generics.rs: copies generic types per use (Stack(Int)).
  • src/loader.rs: loads a program from several files (require). src/modules.rs expands include/extend and module functions before checking.
  • src/pkg.rs: veya.toml, veya deps (git checkouts and the lock file), and finding a package for require.
  • src/ffi.rs: lib blocks checked into C signatures (codegen/ffi.rs and clif/ffi.rs lower the calls, rt/src/ffi.rs has Pointer's memory access).
  • src/sys.rs: one table of system calls (files, directories, ENV, the clock) that both backends lower the same way, onto rt/src/sys.rs. src/prelude.rs adds library code written in Veya (src/prelude/*.veya) to programs that use it.
  • src/desugar.rs: rewrites shared by both backends. Hash methods with a block become loops over entry numbers written in ordinary syntax, so break, next and iterator fusion work as everywhere else.
  • rt/: the runtime in Rust (strings, arrays of any element type, hashes, printing, JSON encoders and the JSON parser, sockets, fork). The C backend links it too, for Hash. build.rs compiles it as a static library embedded in the compiler (for executables), and the compiler also links it directly (for the JIT).
  • runtime/*.h: the C backend's runtime.

Memory conventions in the generated code:

  • every expression produces an owned value;
  • parameters are borrowed;
  • named locals and temporaries are released when the function returns. Cranelift emits the releases in the common exit block, and the C backend uses __attribute__((cleanup)).

All examples and apps run with zero leaks under macOS leaks on both backends, and the C backend runs them with no AddressSanitizer errors. Cranelift's IR verifier checks every generated function. Reference cycles between classes are not collected yet.
